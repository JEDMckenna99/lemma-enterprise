Add sign-in in one element

Drop the button on your page, then wire one backend route. The button handles the popup, the passkey ceremony, and the proof. Full walkthrough with sessions and testing: sign-in quickstart.

HTML
<script src="https://lemma.id/sdk/proof-verifier.js"></script> <script src="https://lemma.id/sdk/lemma-signin.js"></script> <lemma-signin site-id="app.example.com"></lemma-signin> <script> document.querySelector('lemma-signin') .addEventListener('lemma-signin-success', async ({ detail }) => { const res = await fetch('/api/login', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ presentation: detail.presentation }), }); if (res.ok) window.location.href = '/dashboard'; }); </script>

Set site-id to the hostname your users see in the browser (for example app.example.com). That's the only configuration. No registration, no API key, no dashboard step.

What the user sees

First-time visitors get a lemma.id in a Lemma-hosted popup, secured by their device passkey. Returning users just confirm the passkey. Either way your page receives a signed presentation to send to your backend. The same person presents the same ID to your site on every visit, and a different ID to every other site.

Verify on your backend

Never trust a bare ppid from the browser. Verify the signed presentation server-side, then use result.ppid as the account key. Verification is local: your server checks the signature against a cached trust snapshot, with no per-login call to lemma.id.

Node.js
npm install "@lemma.id/proof-verifier@1.4.0"
Python
pip install lemma-proof-verifier # Zero-install alternative: curl -O https://lemma.id/sdk/proof-verifier.py
Node.js login route
import { createVerifier } from '@lemma.id/proof-verifier'; const verifier = createVerifier({ siteId: 'app.example.com', requiredAssurance: 'passkey', }); app.post('/api/login', async (req, res) => { const result = await verifier.verify(req.body.presentation); if (!result.ok) return res.status(403).json({ error: result.reason }); const user = await findOrCreateUser(result.ppid); res.cookie('session', signSession(user.id), { httpOnly: true, secure: true, sameSite: 'lax', }); res.json({ ok: true }); });
Python login route
from lemma_proof_verifier import VerificationContext ctx = VerificationContext(site_id="app.example.com", required_assurance="passkey") @app.post("/api/login") def login(): body = request.get_json() or {} result = ctx.verify(body["presentation"]) if not result.ok: return {"error": result.reason}, 403 user = find_or_create_user(result.ppid) resp = jsonify(ok=True) resp.set_cookie("session", sign_session(user.id), httponly=True, secure=True, samesite="Lax") return resp

Sessions stay yours

After the one verified login, issue your own session cookie or JWT exactly as you do today. lemma.id is not in the request path: protected routes check your session, /logout clears your cookie, and your user table (keyed by ppid) stays on your infrastructure. There is no OAuth token to refresh and no provider outage that can lock your users out mid-session.

Working examples: quickstart includes complete Express and Flask login routes with session cookies.

Prefer your own button? Use the SDK directly

The <lemma-signin> element wraps ProofVerifier. Call it yourself for custom UI. Always pass requiredAssurance: 'passkey' for login.

JavaScript
<script src="https://lemma.id/sdk/proof-verifier.js"></script> <script> const verifier = new ProofVerifier({ siteId: 'app.example.com' }); async function signIn() { const { ok, presentation, reason } = await verifier.verifyForBackend({ autoProvision: true, requiredAssurance: 'passkey', }); if (!ok) throw new Error(reason || 'not_verified'); await fetch('/api/login', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ presentation }), }); } </script>

autoProvision: true lets first-time users create a lemma.id in the popup. Without it, the SDK never opens a popup and returns no_credential for new visitors.

Local development and testing

  • localhost works out of the box: run your site at any http://localhost port with siteId: 'localhost' against the production lemma.id popup. All localhost ports collapse to one binding.
  • Offline tests: mint valid test presentations without a browser or network using the test helpers, @lemma.id/proof-verifier/testing (Node) or lemma_proof_verifier_testing (Python). Your login route tests run entirely locally.

Copy-paste test examples are in the quickstart. Browser requirements: supported browsers (passkeys + WebAuthn PRF).

Troubleshooting

  • siteId hostname mismatch, staging and production subdomains derive different account IDs. Use the exact hostname users see; do not mix www. and bare domain unless that is intentional.
  • Persistent no_credential, pass { autoProvision: true } on your sign-in call. Without it, the SDK will not open the popup for first-time users.
  • Popup blocked or closed, call the SDK from a click handler (not on page load) so the browser allows the popup, and prompt the user to retry if they closed it.
  • revocation_data_untrusted, the local trust snapshot could not be validated (clock skew, stale cache). Retry after a moment; check the system clock if it persists.

FAQ

How do users recover their account?

A lemma.id lives with the user, secured by device passkeys. Users should enroll it on more than one device (phone plus laptop); any enrolled device signs them back in. Passkeys synced through iCloud Keychain or Google Password Manager survive a lost device. There is no password reset because there is no password, and no recovery email because you never collected one.

What happens if I change my domain?

Account IDs are derived from your hostname, so app.oldname.com and app.newname.com produce different IDs for the same person. There is deliberately no "remap my users" API: an endpoint like that would let sites correlate users across hostnames, which the per-site privacy design exists to prevent. Pick your canonical hostname before launch and keep it stable. If you do migrate, run both domains for a window and link accounts yourself: the user signs in on the old domain, your site hands them to the new domain with your own short-lived token, they sign in there too, and your backend, now holding both IDs in one authenticated session, links the rows and carries over any bans or roles. See the quickstart for the full recipe.

Why is there no API key?

Login verification is cryptographic, not permissioned: your backend checks a signed presentation bound to your hostname against a published trust snapshot. An API key would add a secret to leak without adding security. Keys exist only for the optional server-side abuse APIs (PPID blocks), which sign-in doesn't need.

What does lemma.id learn about my users?

Not who they are: no names, emails, or phone numbers exist in the flow. Routine logins verify locally on your servers, so lemma.id doesn't observe when your users sign in. Each site gets a different ID for the same person, so there is nothing to correlate across sites and no data to build an ad profile from.

Is it really free?

Yes. Passkey sign-in is free with no user caps: see pricing. Paid features (human proofs) are a separate step-up you may never need.

Using an AI coding agent?

Point it at llms.txt or the machine-oriented integration guide.

Need one account per verified human?

Sign-in gives you continuity: the same lemma.id always returns as the same account. It does not stop a banned user from creating another lemma.id. When new-account rotation is the attack you're fighting, step up to isHuman human proofs: one verified human per account, on the same integration and the same account ID, by changing requiredAssurance to 'ishuman' on the actions that need it.
