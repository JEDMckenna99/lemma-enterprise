5-minute quickstart

  1. Create a site in the developer dashboard and note your site ID (normalized hostname).
  2. Add the SDK script tag to your page (see SDK Integration below).
  3. Call verify() when you need a human verdict (e.g. on signup, checkout, or a high-risk action).
  4. Read the result: { human, ppid, reason, timeMs } — store ppid on your user/account record.
  5. On confirmed abuse: block that PPID server-side via POST /api/ishuman/site-block (see Revocation). Do not rely on the abuser's browser or wallet to enforce the ban.

What is lemma.id?

lemma.id is an identity-rooted enforcement layer for websites and applications. A user verifies once through a trusted IDV issuer (Didit by default; Stripe Identity supported as a legacy option), then receives an Ed25519-signed credential that can be reused across sites while preserving privacy via per-site PPIDs.

Assurance

Credentials are issued only after a live identity check — liveness detection plus document-to-selfie matching. A bot, AI agent, or stolen ID image cannot obtain a credential, because a live human had to match a genuine government document at issuance.

Core model

The credential is rooted in a verified-person root derived from the IDV result. A master credential is issued for lemma.id; on third-party sites, a Lemma-hosted popup derives a site-specific credential (a per-site PPID) from that person root on first request and stores it for later use. Because the binding is to the person root — not to a wallet, email, or device — resetting any of those does not mint a fresh, clean identity.

What your servers store: nothing sensitive

The live identity check runs at the IDV issuer, and verify() returns only { human, ppid }. Your backend never receives the government ID, selfie, legal name, or date of birth — so you get an enforcement-grade human signal without running a KYC stack or holding the PII that makes identity verification a compliance and breach liability. Store the ppid on your user record; treat it as an opaque per-site identifier, not as sensitive identity data.

Verification Flow

StepComponentWhat happens
1User + IDV issuerUser completes a live identity check (liveness + document-to-selfie match) at a trusted IDV issuer, initiated from /api/ishuman/start-verification. Didit is the default issuer; Stripe Identity is supported as a legacy option.
2Issuer webhookThe issuer webhook (/api/webhooks/didit-identity, or /api/webhooks/stripe-identity for the legacy path) confirms an approved result and records verification state. Issuance fails closed on any non-approved decision.
3Credential issuanceLemma derives the verified-person root and issues a signed verified-human credential (isHuman: true claim) with issuer metadata and TTL.
4Site-proof popupOn a cache miss, the verifier opens a Lemma-hosted popup (/wallet/ishuman-idv) which derives a per-site proof via /api/ishuman/derive-site-proof and returns a signed session presentation.
5Site verifier SDKIsHumanVerifier validates claim, expiry, revocation membership, and Ed25519 signature locally in browser.

SDK Integration

Basic integration uses the hosted SDK and calls verify() when you need a verdict.

HTML
<script src="https://lemma.id/sdk/ishuman-verifier.js"></script> <script> const verifier = new IsHumanVerifier({ siteId: 'your-site-id' }); const result = await verifier.verify(); // result: { human, ppid, reason, timeMs, error } </script>

Constructor options

OptionTypeDefaultNotes
siteIdstringwindow.location.hostnameRegistered site identifier used for per-site proof derivation.
lemmaOriginstringhttps://lemma.idOverride for non-production testing environments.
debugbooleanfalseEnables SDK console logging.
isBlockedLocallyfunctionnullOptional local callback for site-level PPID block checks.

verify() result

verify() returns { human: boolean, ppid: string | null, reason: string, timeMs: number, error: string | null }.

Common reasons include valid, no_credential, expired, revoked, invalid_signature, and site_blocked.

Attach the verification to your own logs

Once a user is verified, you usually want to associate their site-scoped PPID with actions you record — a comment, a checkout, a login, a moderation decision. The SDK gives you helpers to grab the verified identity at any point in your flow and attach it to anything you log. This data lives entirely in your systems — lemma.id stores none of it.

The pattern

Call verify({ autoProvision: true }) once at an entry point (signup, login, first protected action). After that, getPPID(), getVerification(), and stamp() read the cached session with no popup and no network call — safe to drop inline anywhere.

Helper methods

MethodReturnsNotes
getPPID(opts?)Promise<string | null>The verified PPID, or null if not verified. No popup by default.
getVerification(opts?)Promise<Stamp>A compact verification stamp (see shape below) you can log as-is.
stamp(payload, opts?)Promise<Object>Returns a copy of payload with the stamp merged in. Your payload is never mutated.

Options: { key?: string (default 'lemma'), includeProof?: boolean, autoProvision?: boolean }. Pass autoProvision: true to verify-then-stamp at an entry point; otherwise these never open a popup.

You own the data

Treat the PPID as an opaque per-site key: store it on your user/account record and attach it to whatever events you already log. Because the PPID is stable per (person, site), it behaves like a durable user id for that user on your domain — ideal for activity history and, when needed, blocking via Revocation. The optional proof lets you keep cryptographic evidence that a given action came from a verified human, re-verifiable later with the lemma-ishuman-verify backend SDK — all without lemma.id ever seeing your logs.

Revocation and Abuse Controls

Revocation is tiered. Do not rely on the abuser's browser or wallet to enforce a ban.

Tier 0: Immediate site deny (customer app)

Your app should stop the current session immediately (for example end the session, deny the action, or return 403) while Lemma propagates canonical revocation.

Tier 1: Site-bound PPID revocation (immediate, canonical)

Call POST /api/ishuman/site-block with your site API key. Lemma writes both a SiteBlock row and a canonical RevocationList entry for the site-bound PPID, then publishes Bloom sync so verifiers reject that PPID across devices on your site.

You can also revoke IAM users via POST /api/developer/sites/<site_id>/users/<ppid>/revoke, which now triggers the same canonical PPID revocation path.

For local-first verification with ishuman-verifier.js, either call GET /api/ishuman/check server-side or provide isBlockedLocally(ppid) backed by your own synced block list.

Tier 2: Network revocation (reviewed)

Sites can request network action via POST /api/ishuman/network-revoke (tier 1 block is applied immediately). Admin approval through POST /api/ishuman/approve-revocation revokes wallet, master credential, and all derived credentials network-wide.

Privacy Model (PPID by Site)

  • Each site's PPID is derived from the verified-person root and the normalized site hostname (PPID = HMAC(person_root, site_domain)). Binding to the person root — not a wallet secret, email, or device — is what makes a ban survive resets and resource rotation.
  • Derived credentials are site-specific and pairwise-unlinkable; one site's PPID cannot be correlated with another site's PPID.
  • Relying sites receive only a human verdict and their own site-private PPID — never the user's name, ID document, date of birth, or other PII.
  • Issuance and derivation paths preserve separation between the internal site identifier (site_..., used for ownership and database binding) and the normalized hostname (used for PPID derivation and runtime matching).
What lemma.id can and can't see

lemma.id holds the verified-person root that links a person's credentials for re-verification and revocation. It does not retain the raw ID document, and because verification runs locally in the browser, lemma.id does not observe which relying sites a user visits or when they verify. The person root is the deliberate, single correlation point that enables network-wide revocation; sites themselves remain unable to correlate users across domains.
